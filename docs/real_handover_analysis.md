# 双脚着地时 Ready → Policy 切入诊断

下文是增加 settling 实测准入之前的历史实验。当前已补充真实 Start/Ready 故障分析，
见 [Ready 状态检查](ready_posture_failure.md)。仿真脚本现使用新准入条件，结果可能在 A 之前被拒绝。

用户确认：真机按 A 时双脚在地面承重。原报错没有记录关节名和角度，
本机目前也没有对应的 `real_failure_*.json`，因此无法确定那次真机的触发关节。

## 本轮离屏仿真

使用现有 23DoF 模型、真实部署的 `Controller`、`ParkourPolicy`、位置限位、
6 rad/s 目标变化率和 0.8 rad 跟踪保护。机器人从导出的默认姿态开始，
先由固定姿态 PD 承重一段时间，再模拟按 A。策略速度指令始终为零。
物理模型和深度均来自 MuJoCo，没有连接真机或发布 LowCmd。

这是合成初始条件下的 Ready→Policy 实验，不是实际故障录像的回放，
也未模拟整个 Start→3秒渐进姿态流程及真实固件/DDS延迟。

默认条件：固定姿态等待 0.5 秒，按 A 后用当前配置的 1 秒动作渐入。

- 切入时最大关节偏差约 0.182 rad，小于当前准入检查的 0.25 rad，允许进入 Policy。
- 切入后约 0.480 秒，同样触发跟踪误差保护。
- 仿真触发关节为 `right_ankle_pitch_joint`，真实协议槽位 10。
- 原始策略动作约 2.667，缩放后的关节目标约 +0.807 rad。
- 此时渐入比例 0.48，经过渐入、限位、限速后的候选目标为 +0.1985 rad。
- 实测模拟关节角度为 −0.6102 rad，误差 +0.8087 rad，超过 0.8 rad；候选命令未发送。
- 加入实际的状态有效性、倾斜和关节速度保护后，仍在相同位置复现同一跟踪误差。

数据：`logs/sim2real/grounded_handover_validation.json`。
不能把这个模拟关节名称当作尚未记录的真机故障关节。

## 对照说明

在相同 0.5 秒承重准备条件下，只改变仿真的动作渐入时长：

| 渐入时长 | 结果 |
| --- | --- |
| 0.05 s | 切入后约 0.405 s 触发左踝跟踪保护 |
| 0.2 s | 该合成场景运行 10 s 未触发；最大误差约 0.773 rad，仍接近阈值 |
| 0.5 s | 切入后约 0.370 s 触发左踝跟踪保护 |
| 1.0 s（当前默认） | 切入后约 0.480 s 触发右踝跟踪保护 |
| 2.0 s | 切入后约 0.585 s 触发右踝跟踪保护 |

另一个临时对照：把策略历史中的上一动作改为上次实际限幅目标对应的动作，
在 1 秒渐入场景中仍触发保护。这不能单独归因于 last_action 语义。

对照说明当前切入过程对承重后的姿态与动态响应敏感；
更长渐入不一定更稳定，较短渐入也不一定解决问题。
单次 0.2 秒实验通过不足以支持直接修改真机参数。
上述实验配置均只在内存中修改，真机 YAML、PD 和保护阈值没有变更。

## 下一步依据

优先分析真实故障快照中的：

1. 触发关节、真实槽位和 measured q/dq 是否持续响应此前已发送目标。
2. A 切入前的姿态、角速度和实际关节偏差，以及是否存在瞬时身体扰动。
3. 策略目标、渐入目标、位置/速度限幅分别改变了多少。
4. 对应的 IMU、速度指令、深度历史及网络输出。

脚底接触地面不能单独证明切入时的姿态已稳定。当前 Ready 主要根据时间到达，
A 准入检查只覆盖关节偏差和摇杆回中；这些条件并不是动态平衡验证。
本轮已确认代码可在合成承重场景下复现同类故障，尚未确认真机那次故障的具体根因。
不以放宽 0.8 rad 阈值或反复按 A 代替定位。

## 复现

```bash
source .venv-parkour/bin/activate
python scripts/validate_real_handover.py --warmup 0.5 --blend 1.0
```

需要 GPU 离屏渲染访问权限。该条件预期触发保护并返回非零退出码。
`--blend` 仅修改这次仿真实验的内存配置，不修改真实部署参数。

真实故障报告的离线分析命令：

```bash
python scripts/replay_real_failure.py logs/sim2real/real_failure_实际文件名.json
```
